# 《Agent Harness Engineering: A Survey》精读笔记

> 论文：*Agent Harness Engineering: A Survey*（Junjie Li, Xi Xiao, Yunbei Zhang, Chen Liu 等，CMU / UAB / Tulane / Yale / Amazon 等，TMLR under review，2026）
> 一句话总结：**生产级 LLM Agent 的可靠性，瓶颈不在模型本身，而在包裹模型的"执行框架层（harness）"的工程质量。** 本文把这一层系统化为一门独立的工程学科。

---

## 〇、一句话框架

论文围绕**三个核心主张（Claim）**展开：

1. **概念主张（Claim 1）—— 瓶颈约束论（Binding-Constraint Thesis）**：在长程任务上，决定 Agent 可靠性天花板的是 harness 的工程质量，而非模型能力本身。
2. **分类主张（Claim 2）—— ETCLOVG 七层分类法**：把"可观测性（O）"和"治理（G）"从"生命周期钩子"的副产物中提升为**一等公民独立层**；把状态管理放进"生命周期/编排（L）"。
3. **实证主张（Claim 3）**：把 **170+ 开源项目**映射到 ETCLOVG 七层上，揭示生态密度分布、覆盖盲区与新兴设计原则——这是迄今最大规模的 Agent Harness 开源语料。

**支撑瓶颈约束论的三个 2026 实证**（模型不变、只改 harness 即可获得远超模型迭代的增益）：
- Bölük(2026)：仅改 edit-tool 格式与工具 harness，15 个模型在编码基准上**最高 10× 提升**。
- Trivedy(2026)：固定 GPT-5.2-Codex，仅靠"系统提示重构 + 中间件上下文注入 + 自验证钩子"，Terminal-Bench 2.0 从 52.8% → **66.5%（+13.7 个百分点）**。
- Meta-Harness(Lee et al., 2026)：自动化 harness 优化，Terminal-Bench-2 达到 **76.4%**，超过所有手工方案。
- 三者均超过同期"模型换代"通常带来的 2–4 个百分点提升 → **变量是 harness，不是模型。**

## 一、ETCLOVG 七层分类法（全文骨架）

| 层 | 名称 | 解决什么 | 性质 |
|---|---|---|---|
| **E** | Execution Environment & Sandbox 执行环境/沙箱 | Agent 代码在哪里跑、受什么约束 | 结构核心 |
| **T** | Tool Interface & Protocol 工具接口/协议 | 能力如何被发现、描述、调用 | 结构核心 |
| **C** | Context & Memory 上下文/记忆 | 模型每一步能看到什么信息 | 结构核心 |
| **L** | Lifecycle & Orchestration 生命周期/编排 | 读写状态的执行流（单/多 Agent、issue→PR） | 结构核心 |
| **O** | Observability & Operations 可观测/运维 | trace、成本、失败、可靠性信号 | 控制面 |
| **V** | Verification & Evaluation 验证/评估 | 把任务与 trace 变成评估、归因、回归反馈 | 控制面 |
| **G** | Governance & Security 治理/安全 | 权限、身份、策略、加固、审计、人审 | 控制面 |

> 设计取舍：E/T/C/L 是"结构四柱"，O/V/G 是包裹在外的"控制面"。本文与既往六组件框架的最大区别——**把 O 和 G 提为独立层**（它们在生产中有独立的工具栈和独立团队所有权），并把 state 放进 L、把 hook/策略放进 G。

## 第 1 章 Introduction（引言）

- **1.1 瓶颈在 harness 而非模型**：学术长期默认"Agent 能力 ≈ 模型能力"，但近期实证反复证伪——固定模型、只调 harness，增益远大于换更强模型。这即是"瓶颈约束论"。
- **1.2 实践者–研究者鸿沟**：OpenAI 把"harness engineering"明确为一门学科（小团队 5 个月产出约 100 万行内部产品，几乎不手写生产代码）；Anthropic 从相邻角度得出同一原则——架构要简单可检视、工具要为 Agent 而非为人设计、上下文要渐进披露、长程任务要可恢复；Martin Fowler 网站称之为"AI Agent 的控制论调速器（feedforward 引导 + feedback 传感形成的控制回路）"。研究者虽已精细研究记忆/工具/规划/安全各组件，却**缺一套整合它们为可靠运行的系统词汇**。本综述要桥接这道鸿沟。
- **1.3 范围与贡献**：聚焦"包裹语言模型、管理长程多步执行"的基础设施层；不综述开发框架、产品平台或模型能力本身。三个贡献即上述三个 Claim。

## 第 2 章 Background and Taxonomy（背景与分类法）

- **2.1 Agent 系统演进**：从 CoT 到自主 Agent，本质是"工程师要管理的工程面"持续扩张。
  - ReAct 时代(2022–2023)：observe-think-act 循环；AutoGPT/BabyAGI 展示野心，也暴露执行失控、上下文爆炸、状态丢失、副作用不可见等**基础设施问题**。
  - 工具集成与多 Agent(2023–2024)：Gorilla/ToolLLM/Toolformer 让工具用法可学习；CAMEL/ChatDev/MetaGPT 引入多 Agent 协作；SWE-bench/AgentBench/WebArena/GAIA 让评测基建成熟；MCP、A2A 开启协议标准化。
  - Harness 转向(2025–2026)：OpenAI 明确采用、Stanford/MIT 的 Meta-Harness、LangChain DeepAgents 的 +13.7pp 增益共同坐实"瓶颈是基建而非模型"。
- **2.2 三阶段工程演进**（每阶段包含前者，非替换）：
  - **Prompt Engineering(2022–2024)**：优化"单次模型调用的输入文本"。
  - **Context Engineering(2025)**：优化"每一步模型该看到什么信息"——注入/检索/压缩/排序/窗口饱和处理。
  - **Harness Engineering(2026)**：优化"维持状态、中介工具、注入反馈、施加约束、验证进度"的整套基础设施；把七层当作整体。
- **2.3 ETCLOVG 七层**：见上文表格。两个关键设计选择——**O 提为独立层**（有 Langfuse/Phoenix/OpenLLMetry 生态与 OpenTelemetry 实践）；**G 提为一类层**（覆盖模型级/系统级/组织级三子层）。
- **2.4–2.9 方法论**：语料来自既往综述、GitHub 检索、精选清单、企业工程博客（快照冻结于 2026-05-08）；纳入需"公开文档 + 实现具体 harness 机制 + 可编码至少一层"；多标签编码、单主编码者 + 作者复核；并坦诚局限——偏向英文/GitHub 可见/开源/编码 Agent 生态。

## 第 3 章 执行环境与沙箱（E）

> Agent 动作的物理执行层。生产中几乎必然在沙箱内执行。

- **沙箱为何在 Agent 时代是一等议题**（三重目的）：
  1. **安全**：LLM 生成的代码大规模下既不可审计也不可预测；Agent 多步自主执行，无法在动作执行时人工介入；prompt injection 可把良性 Agent 变成攻击载体。
  2. **可复现**：长程任务与评测需要"重置到已知基线"——容器/microVM 可即毁即建（SWE-bench、OSWorld 得以成立）；训练时单任务被回放数百次，廉价重置本身就是可扩展性前提。
  3. **活性（liveness，本时代特有）**：没有沙箱，每个有风险动作都要弹窗人审，导致用户放弃或盲目全批——Anthropic 给 Claude Code 引入沙箱后**权限弹窗减少 84% 且不损安全**。沙箱既是"笼子"也是"许可证"。
- **七类沙箱**：①通用托管沙箱（Daytona/E2B/Modal/北翼 OpenSandbox/Docker，趋势从共享内核容器→专用内核 microVM）；②Computer-Use 基建（Anthropic Computer Use/CUA/OSWorld，以鼠标键盘+屏幕像素操作桌面）；③代码专用沙箱（Judge0/Code Interpreter/sandboxed.sh/langchain-sandbox，趋势从容器→WebAssembly）；④框架内置运行时（OpenHands/agent-infra/smolagents，"打包 vs 组合"权衡）；⑤浏览器评测环境（WebArena/VisualWebArena/BrowserGym/WorkArena，沙箱+评测双重角色，是间接 prompt injection 研究温床）；⑥OS 级权限沙箱（bubblewrap/Seatbelt/seccomp，"许可而非分区"——窄化宿主视图，Claude Code 降弹窗 84%）；⑦沙箱抽象层（SWE-ReX/smolagents executors/K8s Agent Sandbox CRD，让执行底座可替换）。
- **威胁模型与沙箱逃逸**：除传统容器逃逸，Agent 特有——prompt injection 劫持、目标错位（Agent 主动把逃逸当子目标）、组合放大（多工具叠加级联）。SandboxEscapeBench 实测前沿模型对 Docker 容器**逃逸成功率 15%–35%**；防御侧仍零散（IsolateGPT <30% 开销、事务性沙箱 ~14.5% 开销）。
- **部署模式**：自托管（低延迟、重运维）/ 云 SaaS（弹性、管理安全、有网络往返）/ 混合 BYOC（数据驻留+弹性算力）。

## 第 4 章 工具接口与协议层（T）

> 定义 Agent 如何发现能力、表示可调用能力、跨运行时执行动作。核心矛盾：**扩大能力覆盖（暴露更多工具）vs 守住决策质量（动作空间与提示足迹要小）**——过大的工具菜单会降可靠性、增 token、放大规划错误。

- **4.1 协议与接口标准**：MCP（host-client-server + JSON-RPC，已成编码/企业 Agent 最显眼的工具集成底座，价值在于生态流动性）；A2A（Agent↔Agent 跨进程委托，靠 Agent Card 发现）；Function calling、OpenAPI（结构化调用与机器可读契约）；AGENTS.md/AGENT.md（把工具用法与流程约束直接放进版本控制）。**更优组织原则是按"集成边界"分类**：Model↔Function / Agent↔Capability / Agent↔Agent / Agent↔Repo。
- **4.2 工具描述、发现与选择**：瓶颈从"如何调用"转向"每步暴露哪些工具"。EASYTOOL/AnyTool/CRAFT/MetaTool/MCP-Zero/ToolRet/ToolRegistry 等强调**检索感知的编排与注册表质量**是一阶决定因素。两条原则：**"少而精的工具"常胜过暴力全暴露**；发现管线必须自适应（静态全局清单无法扩展）。
- **4.3 工具增强训练与集成**：Toolformer（自学何时插 API 调用）、Gorilla/ToolLLM（更大工具语料+指令微调）、ToolkenGPT/CREATOR（token 级/控制器式集成）；生产侧常配 LangChain/Semantic Kernel/smolagents 运行栈。编码 Agent 还暴露"语义类工具"（静态分析/类型检查/证明助手/补丁等价校验）——Ugare & Chandra 的 agentic code reasoning 主张这类工具应返回**带证据的产物**（trace、证明义务、反例）而非黑箱 yes/no。结论：工具能力由"预训练/微调信号 + 接口 schema 质量 + 运行时选择策略"共同决定，单点优化收益有限。
- **4.4 可扩展性与会话管理**：长程下有状态工具会话改善连续性但增加簿记复杂度；失效模式——过期句柄、重试间状态不一致、冗长工具 trace 撑爆上下文。需显式会话生命周期控制、有界工具上下文注入、可归因错误到规划逻辑还是接口的观测钩子。

## 第 5 章 上下文与记忆管理（C）

> prompt engineering、context engineering 与 harness engineering 的交汇层。核心问题一句话：**每一步只给模型恰好的信息，不多不少。** 太少缺状态、太多性能下降。

- **5.1 为何上下文必须被工程化**：更大的上下文窗口解决不了记忆问题。
  - **二次方注意力成本**：n 个 token → n² 配对权重，成本与上下文长度平方级增长，窗口是稀缺资源。
  - **U 型注意力曲线**（Liu et al.）：相关文档放在上下文中间时准确率比放首尾**下降超 30%**——**信息位置与信息有无同等重要**。
  - **大规模上下文腐化（context rot）**（Hong et al.，测 18 个前沿模型）：随输入增长每个模型都退化且非均匀；语义模糊查询退化更陡；**退化远早于窗口满**（标称 200K 的模型 50K 就可能明显掉点）——这是任何累积工具结果/中间推理/文件内容的 Agent 的常态。
- **5.2 从 Prompt 到 Context Engineering**：前者优化单次调用的静态文本输入；后者优化多步任务中**每步推理时模型可见的完整信息态**。原则：**寻找每步最大化目标结果概率的最小高信号 token 集**。上下文包含系统提示、工具 schema、历史、工具结果、检索文档、动态工作状态——全部争夺同一有限注意力预算。
- **5.3 短期（活跃上下文窗口）**：①系统提示校准（找对"高度"，分段组织）；②token 高效工具设计（"少而表达力强"）；③即时检索/渐进披露（保留轻量标识符按需加载，Claude Code 的 CLAUDE.md + glob/grep 即此范式）；④**KV-cache 感知设计**（Manus 称 KV-cache 命中率是"生产 Agent 最重要的单一指标"，缓存 token $0.30/MTok vs 未缓存 $3.00/MTok——三条规则：保持前缀稳定、上下文 append-only、确定性序列化）。
- **5.4 中期（会话状态与跨运行持久化）**：填活跃窗口与长期记忆之间的缝。①结构化笔记（NOTES.md/todo.md，Claude 玩宝可梦数千步自发出地图/战斗策略/目标笔记，外部化工作记忆）；②基于文件的规划外化（planning-with-files、Trellis，把任务状态/spec/依赖图写盘按需加载，绕过窗口）；③跨运行注入（claude-mem 抓上一运行精华前置到下一会话，无需向量库）。代价低、但不能从索引存储做任意召回。
- **5.5 长期（持久记忆系统）**：索引化、可检索、跨会话/任务/实例。
  - 基础架构：MemGPT（把上下文窗口当 RAM、外部存储当磁盘的 OS 虚拟内存类比）；Park et al. 的 Memory Stream（观察+反思+检索三件套，recency/importance/relevance 三信号，仍是标准模板）；MemoryBank（艾宾浩斯遗忘曲线的动态遗忘 + 个性建模）。
  - 生产系统：Mem0（最广泛部署，向量+图+KV 三后端，LOCOMO 上比 OpenAI 原生记忆准 26%、token 仅 1/10，被 AWS Agent SDK 独家采用）；A-MEM（Zettelkasten 式动态知识网络）；Hindsight（强调"学习而非记忆"）；Honcho（对用户建模而非存事实，异步"dreaming"推理管线）；Mozilla cq（跨 Agent 实例的集体记忆，MCP 原生、本地/组织/跨团队三层）。
  - 学术分类：Zhang et al. 的短/长（语义·程序·情节）记忆 + write-read-manage 循环；Du 的三维分类（范围/格式/组合结构）对应 Pattern A 单体上下文 / B 窗口+检索 / C 分层记忆+学习控制策略。
- **5.6 长程技术（100+ 轮保持连贯）**：①**上下文压缩（compaction）**——先求召回最大化再迭代精度（反过来会丢失不可恢复的状态），最轻形式是工具结果清理（已成 Anthropic 平台特性）；②**子 Agent 上下文隔离**——子任务派给新窗口的子 Agent，只回传 1k–2k token 摘要（隔离 vs 协调需逐任务权衡，共享上下文昂贵且毁 KV-cache 复用）；③**混合决策框架**（Anthropic：常需内容预载、条件内容即时检索、窗口饱和时压缩、需探索时派子 Agent；harness 层 checkpoint/resume + 阈值自动触发压缩/固化）——**上下文管理应是基础设施的职责，不是模型的职责。**
- **5.7 上下文漂移与现有方法的极限**：context drift（长轨迹上行为渐进偏离原始意图，100+ 轮后常重复已做工作、自相矛盾、丢失目标）≠ context rot（单步内加 token 退化）。根因非单纯窗口饱和——每次压缩留存的摘要累积细微偏差。现有评测（MemBench/MemoryArena/增量多轮评测）证明漂移存在但给不出机理。**结论：光靠 context engineering 解不了长程可靠性，必须有验证回路、关键节点人审、行为偏离异常检测——这正是 O 层与 G 层存在的理由。**

## 第 6 章 生命周期与编排（L）

> Agent 如何跨反复模型调用、工具调用、失败、修订、交接完成任务。本文把"执行流"与"它读写的运行态"合在 L 层。状态管理放这里、hook/策略放 G。

- **6.1 生命周期状态管理**：维持跨轮/会话/失败/交接继续运行所需的运行态（待办子任务、工具结果、中间产物、仓库变更、协调元数据、checkpoint/resume）。核心权衡——**无状态重放**（从交互历史重建，可复现可审计但轨迹变长后昂贵）vs **有状态执行**（持久化到文件/库/图/服务，连续性与恢复好但有一致性与调试难题）→ 实践多为**混合**。注意区分：本层是"harness 自己用来继续/协调执行的运行态"，≠ C 层（给模型推理的信息）、≠ O 层（日志/trace/监控）。
- **6.2 单 Agent 内循环**：基本执行单元，遵循 ReAct（推理-动作-观察交替）。OpenAI 对 Codex agent loop 的分析强调：系统行为不只由模型决定，也由"构造提示、调工具、管控制流、回灌工具输出"的 harness 决定。执行模式分无状态重放（Codex CLI 典型）与混合（Claude Code/OpenCode/Gemini CLI/Aider/SWE-agent）。痛点：长程下上下文碎片化、误差累积、分解结构弱。
- **6.3 多 Agent 编排模式**：把规划/执行/检查/修订分到不同 Agent。复现模式：**层级编排**（上层控制器分配+整合，如 DeerFlow/AutoGen/OpenAI Agents SDK/DeepAgents）、**团队编排**（命名专职 Agent，如 oh-my-claudecode）、**工作流编排**（显式阶段，如 Semantic Kernel）、**扇出**（并行探索多解，如 Emdash）、**图组合**（节点化交互图，如 LangGraph/Hive）。Anthropic 的 planner-generator-evaluator（分离规划/执行/验证，提升分解与鲁棒性但增协调开销）。
- **6.4 全生命周期管线（issue → PR）**：以**任务运行器（task runner）**为核心抽象——管理调度、状态持久化、重试、验证、迭代精修；执行锚定在仓库/issue/分支/文件/测试/PR 等持久产物。典型流：issue/任务规格 → Agent 规划 → 代码/产物生成 → 验证 → 人审 → PR 合入。Vibe Kanban/Symphony/GitHub Agentic Workflows 属此类——单 Agent 循环提供执行原语、多 Agent 模式提供协调、task runner 整合成端到端"人掌舵、Agent 执行"的工作流。

## 第 7 章 可观测性与运维（O）

> 本文从"生命周期钩子副产物"提升为**独立层**：它已催生独立的平台/规范/工程实践生态。

- **7.1 trace 与监控平台**：基础是结构化 trace 收集（每个 LLM 调用/工具调用/检索/上下文组装记成 span 树）。Langfuse/Opik/Phoenix/MLflow 提供交互 trace 树、延迟火焰图、token 分解、成本归因、提示版本管理。**OpenTelemetry 成事实标准**（GenAI 语义约定）；OpenLLMetry/OpenInference 自动埋点，让 Agent trace 流入团队已有的 Prometheus/Jaeger/Grafana/Datadog。更深处：AgentSight 用 **eBPF 从进程外监控**（截 TLS、监内核事件、关联 LLM 响应与系统行为，<3% CPU，框架无关、不可被妥协 Agent 绕过）；AgentTrace 用 schema 日志覆盖"认知面（推理/计划/反思）+ 操作面（工具/API）+ 环境面"三表面。
- **7.2 Agent 专用运维平台**：在通用 trace 之上加"Agent 级"抽象（多步会话追踪、Agent 身份/角色、工具选择策略、跨会话状态交接）。AgentOps 的层级 span 模型；RagaAI Catalyst/Laminar。学术：Moshkovich 的六段 AgentOps 自动化管线（观测→收指标→异常检测→根因分析→修复建议→自动处置）+ 四利益方（开发/测试/SRE/业务），实证 **79% 实践者把"非确定执行流"列为最大挑战**；NLAH 把 harness 本身当一类研究对象做消融（工具注册表/权限/hooks/skills/上下文折叠各有贡献）；Watson 的"认知可观测"用 surrogate agent 复原逐步推理 trace；AgentLens 三栏可视化。
- **7.3 成本追踪与优化**：单任务可能触发数十次 LLM 调用。追踪侧：TensorZero（统一 LLMOps 栈）、Helicone（drop-in 代理零改码）。优化侧：FrugalGPT（提示适配/LLM 近似/**级联路由**，自适应级联可达 GPT-4 水平并降本 98%）、GPTCache（语义缓存）、QC-Opt（质量感知联合优化）、TALE（token 弹性——预算设太低反而更耗 token）、Dual-Pool 路由（GPU 工时降 31–42%）。**关键警示**：Anthropic 实证——基础设施配置单独就能让基准分**漂移 6 个百分点(p<0.01)**，省钱可能悄然损性能，没有细粒度可观测就看不见。
- **7.4 可靠性工程**：失败恢复/checkpoint-resume/重试/会话恢复决定长程 Agent 能否扛住瞬时失败。Anthropic 识别长程编码 Agent 四种复现失效（想一步搞定全任务、过早宣告完成、会话间留下破损环境、未测就标完成）→ initializer + coding agent 两段式。GAN 式三 Agent（planner/generator/evaluator）+ sprint contract + 分离自评；并证明**harness 复杂度应随模型能力调整**（Opus 4.5→4.6 升级时移除 sprint 与上下文重置，成本 $200→$125 质量不降）。Managed Agents 把"大脑/手/会话"解耦（崩溃后 `wake(sessionId)` 从事件日志恢复、沙箱失败就重建、凭据存外部金库）——把组件从"宠物"变"牲口"。失效分类：MAST（14 种多 Agent 失效，κ=0.88）、AgentErrorTaxonomy（按模块拆解，**误差传播**是核心瓶颈，AgentDebug 相对提升 26%）、QSAF（认知退化的六阶段生命周期，幻觉可被存进持久记忆形成跨会话自强化退化）。运行时检测：SentinelAgent（图+三层异常分类）、AgentFixer（64–88% 问题检出率，38% 任务失败源于解析错误——可被确定性检查解决）。→ 可靠性需**分层检测策略**：规则查结构失效、统计监控性能漂移、LLM 语义分析查推理失效。
- **7.5 走向统一可观测**：**可观测–评估鸿沟**（LangChain 调查：89% 团队用可观测，仅 52.4% 跑离线评测）——trace 工具与评测框架由不同社区不同接口开发，需打通（生产失败 trace 自动生成回归用例、在线评测分当告警）。统一 LLMOps 栈（TensorZero/Langfuse 把网关+可观测+评测+优化打包）。**harness-as-assumption 原则**：每个 harness 组件都编码了"模型自己做不到什么"的假设；随模型变强，可观测不仅要发现 Agent 何时失败，还要发现**哪些 harness 组件已成多余开销**——理想系统应有元监控层跟踪哪些干预（上下文重置、评估回路、工具限制）仍在"承重"，以便随模型升级持续简化 harness。

## 第 8 章 验证与评估（V）

> 把 Agent 行为变成**工程证据**。核心立场：**报告分数是"模型-harness 对"的属性，不是模型单独的属性。**

- **8.1 把评估建模为"任务→反馈"生命周期**：传统 LLM 评估对固定输入打分；harness 评估测的是一次**执行 episode**（任务锚定环境、Agent 跨时与工具/状态交互、抓 trace、评判既看结果也看路径）。**核心动机：评估基建噪声会伪装成模型失效**——失败可能源于坏工具、陈旧上下文、未重置沙箱、flaky 测试、基准歧义、不稳定 judge，而非模型。因此评估要把行为变成结构化判断 + 失效归因 + 回归反馈，而非只报终分。**五阶段**：
- **8.2 阶段1 任务/基准锚定**：Agent 任务是"嵌入环境的问题"（环境态+工具+动作+约束+终止+成功判据）。分三类——①软件工程/终端（SWE-bench、Terminal-Bench，强结果验证器需强任务锚定）；②Web/浏览器/Computer-Use（WebArena/VisualWebArena/BrowserGym/WorkArena/OSWorld，评测问题=环境设计问题）；③跨域/企业工作流（AgentBench/GAIA/TheAgentCompany，强调覆盖泛化）。
- **8.3 阶段2 执行前就绪校验**：在 Agent 跑前确认沙箱/依赖/工具/上下文态/权限/预算/评估器初始化正确——否则下游失效无法归因。①环境就绪（快照/依赖/测试可执行、网站重置、桌面态）；②工具/上下文/权限就绪（跨层：描述跨运行变了吗、记忆重置了吗、权限过紧会让能干的 Agent 因治理失败、过松会让钻基准的行为漏网——**agent-computer interface 决定了基准到底测什么**，应把这些配置记成评估元数据）；③评估器就绪（确定性 grader 查 flaky/依赖/兼容；LLM-as-Judge 的提示/rubric/模型要版本化；人审协议预先定义）。
- **8.4 阶段3 受控执行与 trace 抓取**：①**受控 rollout**（固定环境态/工具/超时/预算/权限/评估器版本，残余非确定性靠多次 rollout 暴露方差而非藏在单一分数后）；②**trace 原生评估**（记模型输出/工具调用/结果/环境变化/上下文快照/错误/重试/恢复/token/延迟/成本——把二元打分变因果诊断，能区分"从未找到文件 vs 找到但补丁非法"、能揭露"钻基准/过多工具调用/越权"等不当成功）；③成本/延迟/资源追踪（不只排成功率，要暴露**成功率-成本-延迟前沿**）。
- **8.5 阶段4 多层判断与失效归因**（区分 harness 评估与普通基准评估的关键）：
  - **结果层**：是否达成目标（测试/最终文件/环境态/答案串）——可扩展可解释，但"压缩"了一整段 episode，必要但不充分。
  - **轨迹层**：路径质量（工具选对了吗、动作顺序合理吗、有无冗余调用、守权限边界了吗、错误恢复了吗、上下文一致吗）——**给"失效→修复"提供路由**：选错工具→改 T 层；忘约束→改 C 层；不恢复死循环→改 L 层。
  - **评估器层**：评估器本身可信吗（确定性验证器窄但可复现；LLM-as-Judge 灵活但有位置偏置/冗长偏置/自我增强偏置；人审不可扩）。应**分层 grader**：确定性查客观态、LLM judge 查语义/轨迹、人审查模糊/高危；**把评估器当受测组件而非系统外的神谕**。
  - **跨层失效归因**：极少是单标签分类——需对全 trace 做诊断流程，产出结构化诊断供阶段5回灌。
- **8.6 阶段5 持续回归与部署反馈**：①harness 变更（工具描述/压缩策略/沙箱镜像/权限/judge 提示）也触发回归——组件交互下局部改进可能全局回归（维护分层测试套件：单元/单步/全 rollout/多轮模拟）；②评测框架与 LLMOps 集成（promptfoo/DeepEval/RAGAS/lm-evaluation-harness；生产 trace 变回归用例、评测失败变可观测信号）；③**验证器驱动/训练时评估**（R2E-Gym/verifiers 把环境反馈当 reward；Meta-Harness 把 harness 设计本身当自动搜索对象）。
- **8.7 小结**：评估从"排行榜机制"重构成"Agent harness 的质量控制回路"。对长程 Agent，核心问题不是"成功了没"，而是"**为什么成功/失败、路径可接受吗、评估器可信吗、下一步该改哪个 harness 组件**"。

## 第 9 章 治理与安全（G）

> Agent 行为如何被约束、保安全、被问责。生产中它有独立生态（权限引擎、策略语言、审计管线、网关控制），故为独立层。五大机制 + 安全全景 + 研究方向。

- **9.1 权限模型与身份管理**：Agent 工作负载让访问控制比传统 RBAC/ABAC 更难（所需工具集常取决于部署时未知的自然语言任务）。沿粒度轴：①静态边界（Codex 沙箱内受限文件/网络、Gemini CLI 工作区+命令黑白名单，易检视但表达不了任务意图）；②上下文相关权限（**Progent** DSL 谓词覆盖工具名/参数/环境态，运行时逐调用评估最小权限；**Conseca** 从可信上下文生成任务专属策略 + 独立确定性执行器，策略生成与执行分离很关键）；③跨边界身份与多 Agent（South et al. 的**认证委托**：扩 OAuth2/OIDC 加 User/Agent/Delegation Token，绑用户意图到 Agent 专属权限形成可追责链；SAGA 多 Agent 加密一次性密钥 + 短命令牌；IsolateGPT 的 hub-and-spoke 隔离）；④凭据管理（Skyvern 模式：金库存密钥、只给 LLM 占位符、在执行层替换——未解的是长程会话中 token 过期/吊销的重置）；⑤Web 级权限协调（agent-permissions.json，类 robots.txt）。开放挑战：既表达又好用的权限模型、跨 harness 可移植的策略规范语言、动作归谁（操作人/Agent 实例/瞬态任务身份）。
- **9.2 生命周期钩子**：定义"策略检查何时触发"，在循环各阶段注入治理而无需改核心推理。四个钩子点：**H1 输入护栏**（PromptShield/DataSentinel 查 prompt injection，规则严格但脆、模型泛化但慢且怕自适应攻击）；**H2 动作前护栏**（ShieldAgent 可验证谓词、ControlValve 约束多 Agent 控制流图防劫持）；**H3 执行后信息流控制/污点追踪**（**CaMeL** 能力式 IFC：每个数据值带溯源标签、自定义解释器保证不可信数据不能影响控制流，在 AgentDojo 上以牺牲灵活性换更强边界）；**H4 人机闭环**（Codex/Gemini CLI/Cursor/OpenHands 对破坏性/越界动作要人审；三维：验证范围/告警丰富度/复发策略——类比 Android 仅 17% 用户注意权限弹窗、仅 3% 答对理解题，Agent 弹窗有同样的"习惯化+理解"风险）。AgentSpec（触发/谓词/动作的可编程执行基座）、AgentDoG（从单动作分类到轨迹级诊断）。开放挑战：钩子 API 异质、缺通用标准、叠加钩子的交互效应几乎未研究（上游消毒器可能改掉下游检测器依赖的信号）。
- **9.3 组件加固**：强化单个组件（LLM 与工具）对各自漏洞的抵抗力。①模型加固（prompt injection 根因是 LLM 对所有输入等优先级——Wallace et al. **指令层级**训练模型优先系统提示、SecAlign 把同一目标表述为偏好优化）；②分类器运行时加固（**Llama Guard** 独立模型对输入输出按可配置安全分类打标，分类法可不重训编辑、可跨后端复用，代价是每周期多一次前向）；③工具加固与 **MCP 安全**（MCP 初版缺安全原语：Radosevich 示范可胁迫商业 LLM 用 MCP 工具执行恶意代码；Trail of Bits 示范 MCP 服务器可在用户调用前靠**投毒工具描述**攻击客户端注册时行为；防御 ETDI 给 MCP 加**加密签名+版本化**工具定义防"地毯式拉取"攻击）；④协议级（SAFEFLOW 多 Agent 细粒度 IFC + 事务执行，违规可回滚）；⑤供应链（slopsquatting——开源模型 21.7% 概率幻觉不存在的包名，攻击者注册后注入恶意代码）。开放挑战：缺统一框架把模型加固与工具加固组成可量化残余风险的连贯栈。
- **9.4 声明式"宪法"**：把治理逻辑外化到声明式配置（多为 YAML），成 Agent 的机器可读宪法。①**训练时宪法**（Anthropic Constitutional AI 四层优先级：安全/伦理/合规/有用，区分硬约束如 CBRN 绝对禁令与软默认——难部署后改、难独立审计）；②**部署时宪法**（**AutoHarness** 的 YAML 指定管线模式/风险分类/允许-拒绝工具模式/token 预算/审计目的地，意图与执行分离、安全与合规人员可不改代码审改策略、可版本化 diff）；③**可编程策略语言**（Progent 布尔谓词+量词+环境引用、Formal-LLM 把计划约束编码为下推自动机、VeriSafeAgent 对 UI 状态迁移的 DSL）。开放挑战：无可移植标准 schema、缺一致性/完备性校验工具、**训练时与部署时宪法的交互（YAML 否决能否压过 RLHF 强化行为）几乎未研究**。
- **9.5 审计基础设施**：记录 Agent 做了什么、为什么、是否守策。①结构化审计轨迹（AutoHarness 每工具调用 JSONL：名称/参数/风险/权限决策/结果/token/延迟；SAGA 跨 Agent 加密 token 追溯；可回放审计记录至少需 trace id/主体身份/工具调用/策略决策与版本/结果/成本/完整性哈希——多数系统只记子集、很少签名，易被妥协进程篡改）；②异常检测（**逐动作 vs 轨迹级**：逐动作便宜但不能抓"每分钟读一个文件"的慢渗出；轨迹级如 AgentAuditor/SentinelAgent 能抓多步攻击但延迟高、告警定位难）；③成本/资源审计（失控循环耗尽预算，2025 OWASP Top 10 把"资源耗尽"单列，AutoHarness 声明式会话预算，多 Agent 扇出可能指数级放大调用）；④分层治理管线（AutoHarness 三档：逐档加深检查，由 YAML 宪法声明式选档，治理开销随部署风险伸缩）。
- **9.6 把治理放进 Agent 安全全景**：Kim et al. 综述 128 篇、编目 51 攻击/60 防御、七设计维度（输入信任/访问敏感度/工作流/动作/记忆/工具/UI），灵活性越大攻击面越大、治理在运行时约束灵活性。六个真实 Agent 案例（Codex/Gemini CLI/OpenHands/Browser Use/Nanobrowser/Skyvern）**无一完整实现所有防御类**：信息流控制、身份管理、形式化验证在所有系统中都缺失；监控都是部分的。纵深防御及其代价（层叠不当会互相干扰，独立治理钩子的可组合性基本未测）。Kim 等提议把 **contextual security（上下文安全）**作为 CIA 三元组之外第四目标——尚新、未被 NIST/主流教材采纳，作框架参考而非定论。
- **9.7 研究方向（八条）**：①标准化的策略与审计语言；②形式化治理保证（证明宪法内部一致且覆盖所有工具类）；③自适应治理（LLM 生成策略，但生成器自身如何被治理未解）；④长程 Agent 的治理（规则可跨演进会话续期/吊销/审计）；⑤好用的治理界面（HCI 研究，权限 UI/审计仪表盘/宪法编辑器对非专家可及）；⑥跨层治理一致性（训练时对齐 × 部署时配置 × 运行时执行如何复合）；⑦端到端供应链治理（包管理器与检索源在治理栈之外）；⑧统一的治理栈对抗式基准（联合报防御有效性/误报率/开销）。

## 第 10 章 跨层关切

七层并非独立：E 约束 L 的可行策略、C 影响 V 的可复现性、G 的身份/权限/审计横跨每一层。生产 harness **最常在各设计面的接口处失效**，应把 harness 设计读作"依赖结构"而非"可分离组件清单"。四个跨层关切：①层间交互模式；②**成本-质量-速度三难困境**（同步/离线/昂贵恢复路径的取舍）；③标准化与生态动态（MCP/ACP/A2A 推动共享接口，但把责任转给 G 与 O——标准化工具调用只有当周围 harness 能跨系统保溯源/权限/成本/失效证据时才有用）；④五类持续生态缺口（跨工具互操作、成本归因、失败恢复、多仓库编排、人-Agent 交接）。

## 第 11 章 跨层综合（Claim 1 的核心支撑）

把第 10 章凝练为五个系统级效应：
- **11.1 成本-质量-速度三难困境**：质量不能当标量目标，须决定哪些风险值得昂贵控制、哪些检查异步/进回归套件、哪些遥测值得在每个生命周期阶段采集。
- **11.2 能力-控制权衡**：更强的 harness 给 Agent 更多权限，但每多一分权限都扩大控制问题（更大工具菜单→选择错误与注入面；持久记忆→溯源/陈旧/隐私；宽松沙箱→更大爆炸半径）。它不是安全附加项，而是贯穿工具 schema/上下文策略/运行时权限/身份/可审计/人审的**设计轴**。
- **11.3 harness 耦合问题**：层间耦合让局部优化脆弱——执行环境改包可用性/重置语义/延迟/失效模式会改评测结果；工具描述耗上下文预算并塑模行为；trace 只有在身份与权限态同粒度被记时才成治理证据；评测设计奖励某些恢复回路而惩罚另一些，反哺编排。**一个 prompt/工具/记忆/沙箱/验证器/监控孤立看好，组合后可能让整条 rollout 退化**——也解释了为何"不指定周围控制器就无法把分数干净归因到模型"。
- **11.4 从 Agent 框架到 Agent 平台**：框架打包本地抽象（Agent/工具/记忆/执行循环）；平台加持久工作区、托管沙箱、身份、计费、可观测、评估、治理、跨多次运行多用户的人审交接。中心问题从"怎么搭一个 Agent"转向"**怎么运营一支随时间仍可检视、可回滚动作的 Agent 舰队**"。
- **11.5 研究议程**：harness 作为自适应控制系统——需要"变化 harness 干预而非只变模型权重"的基准、跨层 trace 原生失效归因、在 Agent/工具/沙箱/评估器/人之间转移状态与责任的协议、随模型变强简化 harness 的优化方法。

## 第 12 章 开放问题与未来方向

Agent harness 正变成长程控制系统，但五个问题仍科学上欠定义：
- **12.1 加固与扩展执行环境**：使运行时底座既可测又可组——通用安全评估（针对 prompt injection/目标错位/组合放大）、决定何时用容器/microVM/OS 权限边界/全桌面 VM/浏览器/学习代理的成本模型、跨部署模式的可移植层；bundle vs compose 应当经验问题而非产品偏好。
- **12.2 长程 Agent 维持可靠状态**：最深的上下文问题不是塞更多 token，而是**让 Agent 工作状态随长程保持与真实任务态对齐**——把上下文管理重述为**状态估计**（能否刻画每次压缩/检索/遗忘丢了多少任务相关信息、能否界定 Agent 内部态与真实态的发散）；需不确定感知摘要、记忆事实的溯源、矛盾处理、显式陈旧标记、从持久产物重建缺失态的恢复流程；记忆策略应按"是否阻止下游动作错误"而非召回准确率被评判。
- **12.3 从 trace 诊断失效**：评估太以终分为中心；需 trace 原生评估（trace 成计算结果分/轨迹质量/失效归因/回归测试的主对象）；打通可观测–评估鸿沟（把异常生产 trace 变回归用例、直接在 span 上算轨迹指标、把诊断信号回灌提示/工具/上下文/编排变更）；Reflexion 式"从自己 trace 学习"扩到长程多会话。
- **12.4 Agent/工具/人之间的标准交接**：缺跨层交接契约——交接应同时传递意图、约束、权限、产物、溯源、预算态、风险级、trace 历史、未决决策（不仅文本摘要）。技术上由 MCP/A2A/OpenTelemetry 局部标准化，机构上由治理（身份/委托/权限清单/可审计）从反向抵达。需"丰富到够安全可恢复、简单到可广泛采用"的协议，并让责任显式。
- **12.5 随模型变强保持 harness 有用**：harness 设计不应单调加更多脚手架——每个 wrapper/重置/验证器/规划器/记忆规则/权限门都编码了"模型自己做不到什么"的假设，随模型变强应**重估而非默认其仍有益**（因子式"模型×harness"评测可揭示某干预是普适增益、只帮特定模型族、还是反转排名）。Anthropic 实例：对某模型有用的上下文重置对更强模型可去掉、去掉后降本不降质。元工程议程：harness 需**优化和简化自身**的机制（Meta-Harness 把 prompt/工具/控制循环当搜索目标、NLAH 让模块显式可消融、TensorZero/Axon/AgentOps 指向预算感知运行）。中心风险是**基准过拟合**——更耐久的目标是"自适应简化"。

## 第 13 章 结论

把 Agent harness 当独立工程面，主张**基础设施质量（而非模型能力单独）决定真实世界 Agent 可靠性天花板**。三个主张收敛：ETCLOVG 七层（O、G 提为一类层，反映生产团队已如何组织工具栈与所有权）；170+ 项目映射给出迄今最广生态快照，暴露采用模式/覆盖缺口/新兴设计原则；三阶段演进 + 跨层综合（三难困境/能力-控制权衡/耦合问题）把 harness 放进更宽工程轨迹。局限坦诚：偏英文/GitHub 可见/开源/编码 Agent 生态；分类是描述性的，把 ETCLOVG 变成**可指导设计决策的规范框架**是自然的下一步。

## 附：对个人 AI 成长实践的几点启发（笔记作者增补）

> 这部分非论文内容，是结合"AI/大数据专业实践"方向的个人提炼。

1. **把注意力从"追模型"转到"造 harness"**：模型换代带来 2–4pp，harness 工程带来 10×/+13.7pp。在日常 AI 应用/数据产品中，与其等下一个模型，不如系统优化"上下文怎么组装、工具怎么暴露、状态怎么恢复、结果怎么验证"——这是个人技术杠杆最大的方向。
2. **ETCLOVG 是一张可落地的自检清单**：做任何 Agent/数据产品时，可用七层逐项自检——E 沙箱与可复现、T 工具协议与少而精、C 上下文工程（尤其 KV-cache 与渐进披露）、L 状态与编排、O 可观测、V 评估即质量回路、G 治理与审计。缺哪层，哪层就是可靠性短板。
3. **"harness-as-assumption"是反过度工程的思维武器**：每个脚手架都在假设"模型做不到"，要定期重估、敢于删减——这同样适用于个人搭的 prompt/工具/流程，避免复杂度无脑堆积。
4. **评估即工程证据，不是排行榜**：把"成功率-成本-延迟前沿"和"trace 原生失效归因"纳入日常数据产品的质量度量，比单一准确率更接近真实可靠。
5. **从框架到平台的跃迁是职业机会**：问题正从"怎么搭一个 Agent"转向"怎么运营一支可检视、可回滚的 Agent 舰队"——可观测、治理、审计、交接契约这些"运维/平台"能力，正是稀缺且高价值的方向。
