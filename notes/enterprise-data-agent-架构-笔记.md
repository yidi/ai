# 企业 Data Agent 架构精读笔记(去产品化 · 技术视角)

> 原文:《企业 Data Agent 架构怎么设计?5 大核心模块一次讲清!》(李启方,微信公众号)
> 阅读目的:剥离产品叙事(FineBI Next),从技术视角提炼 Data Agent 的架构与实现,并与已学的 **ETCLOVG 七层分类法**(见 [[agent-harness-engineering-survey-笔记]])做映射。
> 一句话总结:**企业 Data Agent 的可靠性瓶颈,同样不在模型(L)本身,而在包裹模型的"数据/语义/流程/治理"这一层 harness 质量——这正是 ETCLOVG 在"数据分析"垂直域的具象化。**

---

## 〇、核心论点

文章开篇抛出四个落地即崩的问题,本质都在指向一句话:

> **企业 Data Agent 从来不是在数据库前面接一个大模型,而是要重新组织企业的:数据、知识、分析方法、工具、流程与权限。**

完整执行链路(一条带校验的 Agent 回路):
**理解用户问题 → 识别业务含义 → 拆解分析任务 → 调用数据与工具 → 验证分析结果 → 形成业务结论 → 推动后续行动**

这与 ETCLOVG 的核心主张完全一致:变量是 harness,不是模型。文章相当于把这一主张在 Data Agent 场景下做了五模块的拆解。

---

## 一、5 大核心模块(去产品化总结)

### 模块① 数据与语义模块 —— 让 Agent 看懂企业数据

**痛点**:把大模型直连数据库(NL2SQL),技术上能跑通,但答案未必能用。一句"今年华东地区哪个产品的利润下降最严重",每个词都有业务语义歧义:
- "今年"=自然年还是财年?
- "华东地区"=哪些省/分公司?
- "产品"=大类、产品线还是 SKU?
- "利润"=毛利、营业利润还是净利?
- "下降最严重"=比金额还是比比例?

> 这些不是 SQL 语法问题,而是**业务语义问题**。没有统一口径,Agent 越会写 SQL,错误传播越快。

**解法**:在数据库之上建**统一的数据与语义体系**:
- 数据表、字段及其业务含义;
- 指标定义与计算公式;
- 维度、层级与关联关系;
- 业务术语及同义词;
- 时间、区域、组织口径;
- 数据权限与敏感等级;
- 常用分析模型与计算规则。

**第一设计原则**:**不要让大模型直接猜测原始数据,而要让它在统一、规范、可解释的数据资产体系上工作。** 用户提"销售额",Agent 应优先调用企业已定义并验证过的指标,而非临时拼 SQL。

---

### 模块② 上下文与记忆模块 —— 让 Agent 知道你在问什么

现实分析是**连续对话**,后一问依赖前面的条件("它/这个指标/刚才那几个产品")。记忆分两类:

**短期记忆**(当前会话状态):已问问题、时间范围、已筛选的区域/产品、查询过的数据、分析进行到第几步、指代消解。

**长期记忆**(跨会话/跨任务):用户部门岗位、常关注指标、已确认口径、常用分析路径、异常历史处理经验、不同角色关注重点(销售总监看达成率/区域增长;门店经理看客流/转化率/客单价)。

**记忆治理三问**:**记住什么、保存多久、什么时候该忘记。** 记得越多未必越好——旧指标、过期规则会干扰当前分析。

---

### 模块③ 规划与编排模块 —— 决定下一步做什么(任务中枢)

企业分析往往是一条**多步骤任务链**(例:"分析最近三个月库存积压主因并给建议" → 8 个子步骤)。让大模型一次性干完,易出现步骤遗漏、口径漂移、工具调用错误、中途跑偏。

**编排中枢职责**:识别真实意图、判断复杂度、拆步骤、选数据/模型/工具、排执行顺序、保存中间态、检查完成、失败重试/换路径、高风险环节请求人审。

**核心架构原则**:**能固化成流程的,不要完全交给模型临场发挥;只有无法预先确定的部分,才交给模型动态判断。** 企业需要的是"在明确边界内具备自主能力的 Agent",而非无限自由的 Agent。

把稳定分析方法沉淀为可控流程:
- 查询类:语义识别 → 指标匹配 → 数据查询 → 结果校验;
- 经营分析:趋势 → 结构 → 差异 → 原因;
- 财务分析:盈利能力 / 营运能力 / 偿债能力框架;
- 销售分析:目标 / 趋势 / 结构 / 渠道 / 区域 / 产品逐层拆;
- 高风险写入:最终执行前加审批节点。

> Data Agent 不是推翻原有分析体系,而是在其上叠加 NL 理解 + 任务规划 + 自动执行。

---

### 模块④ 工具与分析执行模块 —— 生成可用的分析资产

没有工具能力的 Agent 只是聊天机器人。常见工具:数据库查询、指标平台调用、数据目录检索、BI 仪表板调用、SQL/Python 计算、数据质量检测、图表生成、知识库与文档检索。

**真正的难点**:**AI 生成的分析结果能不能继续被查看、修改、复核、发布、沉淀。** 普通 AI 问答停在对话框里,对话结束即丢失;企业需要的是"可继续加工的分析起点"。

**AI 降低分析启动门槛,BI 承接后续编辑/管理/发布/复用。** 输出不止一段文字,还可是趋势图、异常明细表、专题仪表板、管理驾驶舱、经营会议故事板、含计算逻辑的复杂财务报表,并通过门户/应用市场/群聊/移动端触达不同角色。

---

### 模块⑤ 安全、评估与行动闭环模块 —— 决定能否上线

很多项目能跑 Demo 却进不了生产,缺的是**安全、评估、治理机制**。Agent 有自主性,可能选不同数据/工具/路径,产出不同结论。

**可观测性**:必须看到完整分析过程——问题、识别的意图、用的指标与口径、选的字段维度、查的数据、执行的计算、生成的表图、结论依据、哪步异常、哪环需人审。

**自动校验 + 人工接管**:
- 口径与标准模型不一致 → 停止输出;
- 查询结果异常 → 重查数据范围;
- 涉敏数据 → 先鉴权;
- 订单修改/任务创建等写操作 → 人审;
- 置信度不足 → 明确提示,不强行下结论。

**行动闭环**(与普通 AI 问答的本质区别):不止"找到问题",还要知道**为什么发生、如何改善、改善是否有效**。

## 二、与 ETCLOVG 七层的映射(技术视角的核心)

把文章 5 模块投射到 ETCLOVG(E/T/C/L 结构四柱 + O/V/G 控制面),可看到文章的价值:**在通用 harness 框架里,企业 Data Agent 把 E(语义环境)做厚、把 L(编排)做可控、把 O/V/G(观测+验证+治理)做严,而对模型本身保持克制。**

| ETCLOVG 层 | 名称 | 文章对应模块 | Data Agent 场景的特殊性 |
|---|---|---|---|
| **E** | Execution Environment & Sandbox 执行环境/沙箱 | 模块①(**核心地基**) | "环境"=**已治理的数据资产**,不是裸库。这是最常被跳过、却决定上限的一层 |
| **T** | Tool Interface & Protocol 工具接口/协议 | 模块④ | 工具≠接 API,关键是产出能否资产化、可被 BI 体系承接 |
| **C** | Context & Memory 上下文/记忆 | 模块② | 短期/长期记忆 + 遗忘治理(记住什么/存多久/何时忘) |
| **L** | Lifecycle & Orchestration 生命周期/编排 | 模块③ | "可控流程优先,临场推理兜底"是核心设计哲学 |
| **O** | Observability & Operations 可观测/运维 | 模块⑤(可观测部分) | 全过程留痕:意图/口径/查询/计算/图表/依据/异常环节 |
| **V** | Verification & Evaluation 验证/评估 | 模块⑤(自动校验部分) | 口径一致校验、异常检测、置信度估算 |
| **G** | Governance & Security 治理/安全 | 模块⑤(权限/人审部分) | 行列权限继承、涉敏鉴权、写操作审批、行动闭环 |

> **诊断**:绝大多数企业做 Data Agent 时,**重 T/L(工具+编排,即"AI 能力")、轻 E/O/V/G(语义+观测+验证+治理)**。这正好对应 harness 论文说的"瓶颈不在模型而在控制面"——产品叙事容易让人盯着"AI 能写 SQL",但真正卡上线的是 E(口径)和 G(权限)。

## 三、成熟度三阶段(演进路径)

| 阶段 | 能力 | 重点 |
|---|---|---|
| ① 准确查数 | NL 查指标/明细/报表 | 数据接入、指标统一、语义口径、权限控制 |
| ② 多步骤分析 | 识别意图、拆分析路径、趋势/结构/差异/原因定位 | 分析模型、任务编排、连续追问 |
| ③ 沉淀资产 + 行动闭环 | 分析表/图/报告可改/发布/沉淀,用于汇报、预警、协同、改善跟踪 | 分析资产沉淀、业务协作、行动闭环 |

**每前进一步,对数据治理 / 流程治理 / 安全治理的要求都更高。** 落地建议:别一上来做"覆盖财务+销售+供应链+生产+人力的万能 Agent";先选**边界清晰、数据基础好、分析方法成熟**的场景打透(如销售目标达成、库存周转、财务经营指标、门店监控、经营分析会、项目风险跟踪),验证价值再扩展。

## 四、扩展思考:各角色/部门需要深钻的细节

Data Agent 是跨团队工程。按数据团队常见分工,把 ETCLOVG 各层的"深钻点"落到角色:

### 1. 数据治理 / 数据资产管理团队 —— E 层的灵魂
- **语义层是核心交付物**:原子指标/派生指标/复合指标的定义与公式、维度建模、业务术语表 + 同义词词典(归一"销售额/营收/GMV")。
- **指标口径治理**:版本化、唯一 owner、变更追溯——口径一变,Agent 历史答案全错。
- **数据目录字段级元数据**:业务含义注释、敏感等级、血缘。
- 🔑 **深钻点**:"NL → 指标"的召回与消歧准确率(同义词扩展、候选排序、歧义反问澄清)。直接决定模块①上限。

### 2. 数据开发 / 数仓团队 —— E 层底座 + T 层执行
- **数据质量**:给 Agent 可靠底座——DQC 规则、空值/异常/波动监控(脏数据进,错结论出)。
- **语义层物化**:建设 Metric Store(指标平台),让 Agent 调用"指标 API"而非裸写 SQL,从源头消灭口径歧义。
- **性能与并发**:Agent 带来大量高频即席查询,需 OLAP 加速、预计算、结果缓存。
- 🔑 **深钻点**:**语义层查询 vs 直查数仓** 的架构权衡、指标平台 API 契约设计(入参/出参/口径说明)。

### 3. 数据产品团队 —— C 层 + L 层 + 交互
- **记忆产品化**:短期/长期记忆形态、个性化分析路径推荐。
- **分析方法论沉淀**:把经营/财务/销售分析的"套路"产品化为可复用 SOP,喂给编排层。
- 🔑 **深钻点**:Agent 交互设计(连续追问、下钻、纠错、指代消解的产品形态);"AI 生成 → BI 承接编辑"的资产沉淀路径。

### 4. AI / Agent 工程团队 —— L + T + O/V 技术核心
- **规划与编排**:任务拆解策略选型(ReAct / Plan-and-Execute / 固定 DAG),**"可控流程 vs 自由推理"的边界**。
- **工具集成**:Function Calling / MCP、工具 schema 描述质量、调用错误处理与重试。
- **评估体系**:离线评测集(NL2SQL 准确率、口径一致率、工具调用成功率)+ 在线监控 + A/B。
- 🔑 **深钻点**:可观测性(trace 每步的意图/口径/查询/计算)、置信度估算、幻觉与口径错误的防控兜底。

### 5. 数据安全 / 权限团队 —— G 层
- **行列权限继承**:Agent 必须以**当前用户身份**鉴权,绝不越权查数(企业上线红线)。
- **敏感数据**:脱敏、分级分类、访问审计。
- **写操作治理**:审批流、操作审计、可回滚。
- 🔑 **深钻点**:Agent 行为合规审计日志、prompt 注入防护(防通过自然语言绕权/执行恶意写)。

### 6. BI / 业务分析团队 —— T 层资产 + 业务对齐
- **分析资产化**:把 AI 一次性输出沉淀为可复用仪表板/报告。
- **业务口径对齐**:与业务方确认指标定义,反哺进语义层(E)。
- 🔑 **深钻点**:建立"AI 结论 → 人工复核 → 沉淀"质量保障机制,做 Agent 与业务之间的最后一道质量闸。

### 协作视角的两条落地结论
1. **不要一上来做"万能 Data Agent"**,先选边界清晰、数据基础好、分析方法成熟的场景打透,验证价值再扩展。
2. **成熟度按三阶段递进,别跳级**——没有 E 层(模块①语义层),L 层(模块③编排)和 O/V/G(模块⑤校验治理)都是空中楼阁。

## 五、与《Agent Harness Engineering》的对照小结

| 维度 | Harness 论文(通用) | 本文章(Data Agent 垂直域) |
|---|---|---|
| 核心主张 | 瓶颈在 harness,不在模型 | 同——瓶颈在数据/语义/流程/治理,不在模型 |
| 瓶颈层 | O(可观测)、V(验证)、G(治理)被低估 | E(语义环境)、G(权限)被低估 |
| E 的含义 | 代码执行沙箱 | 数据/语义资产环境(业务化扩展) |
| 落地哲学 | harness 工程化为独立学科 | "固化流程优先,临场推理兜底" |
| 评估驱动 | 把 trace 变成评估/回归 | 全过程留痕 + 口径校验 + 置信度提示 |

> **一图记忆**:通用 Agent harness 七层是 E-T-C-L + O-V-G;Data Agent 把 **E(语义)做厚、L(编排)做可控、O/V/G(校验+治理)做严、对 LLM(模型)保持克制**。谁先把 E 和 G 补齐,谁就能从 Demo 走进生产。
